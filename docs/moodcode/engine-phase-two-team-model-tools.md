# MC2-06 current execution — actor-bound model team tools

The separate `teamModelTools: true` opt-in requires `teams: true`. It installs a fixed catalogue of `send_agent_message`, `read_agent_mailbox`, `claim_team_task` and `complete_team_task`. Installing the catalogue does not select an actor: the host calls `bindTeamModelTools({rootSessionId, teamId, memberId, generation, childTaskId?, recipientAliases?})` to bind one exact approved member to its actual root or child execution. `releaseTeamModelTools(originalBinding)` removes that selection. Rebinding does not change the tool registry or a frozen catalogue, and an already prepared request cannot borrow a replacement binding.

Binding and invocation capabilities are ORIGINAL objects. The root owner adapter captures actual runtime/session/Run/storage identity; the selected member revision, role, permissions, expiry, team head and owner SHA are pinned. A caller cannot reconstruct them from JSON or a copied binding. Each actual execution has one selected member. A worker or observer alias cannot borrow a coordinator alias for that same execution. The host recipient allowlist is an exact bounded list of member aliases; its default is empty.

The model can supply only the operation's data: send request ID, recipient alias and text; read limit; or task request ID, task ID and expected revision. It cannot select workspace, team, member, generation, root/child owner or native tool identity. Strict parsing rejects extra keys, malformed UTF-8, accessors, proxies and overlarge complete inputs before native team effects. Native task completion remains board metadata, not evidence of coding success or permission to merge files.

The coordinator records each ORIGINAL ToolContext in a WeakMap for its actual preparation or execution operation. The host verifies that original context, live owner, native tool row, Turn, provider Attempt, open tool Part, workspace, storage paths, cancellation signal and selected actor. Matching SQL IDs in a copied context do not establish ownership. Changed descriptors are rejected before getter execution. The native tool input must match the parsed request, and the actual catalogue, policy and member capture are checked again at dispatch.

All three mutations require exact native approval. The outer runtime fingerprint, actual approval row and ORIGINAL running tool owner are checked by the coordinator; the host also binds the inner `teamModelRequestFingerprint` and exact operation snapshot. Generic grants cannot replace that approval. Denial, cancellation, released bindings, stale task/member revisions and changed recipient ownership perform no new native mutation. Reads follow the existing read policy; they are not automatically placed under the write approval rule. An explicitly asking read policy can still hold a captured mailbox page for approval.

Reading captures a complete page, immediately releases its native page capability and returns bounded untrusted observation data. Later sends may append messages without changing that prepared prefix, but claimed cursor changes, a pending delivery, expiry or actor changes invalidate it. Reading does not advance the cursor, acknowledge delivery, wake a child or acquire membership. The default read size is four messages, with an explicit limit from 1 to 64. Inputs are at most 8 KiB, send text is at most 4 KiB, the minimum remaining tool output budget is 1 KiB, and complete model JSON is at most 32 KiB. Overlarge reads fail before returning an incomplete page. A persisted write may return bounded receipt metadata when its full observation exceeds the model output budget; its durable native result remains available through host history.

Child engines retain `teams: false` and `teamModelTools: false`. Only the original owned child constructor receives the root's fixed scoped handlers, and only requested names within the actual parent catalogue are installed. The root must explicitly approve membership and bind that actual child; no default actor, team creation, parent alias or recipient authority is inherited. These four model operations use the existing current child Run and budget. They neither create an additional Run/input nor replenish its reservation.

Provider admission now has a separate original child-handle boundary: the task manager first commits its actual running state and child Run ID, then synchronously releases provider initialization. Actual root/mirror child-storage admission is already complete. Cancellation settles the held wait through the original AbortSignal, so a parent cancelled at the task commit invokes the child provider zero times and can still observe confirmed cleanup. This gate is memory-only; it grants no historical wake or crash replay authority. Normal engine reopening still treats unfinished child execution through existing recovery.

Independent actual Engine/Git/SQLite tests cover root and child model consumption, frozen approval/page behavior, selected-role and profile intersections, denied/cancelled/released/unbound requests, copied context rejection, output caps, close/reopen, fixed child budgets and provider admission ordering. Product integration repairs distinguish read approval from writes and make the admission wait settle on cancellation. Final gate identities and results are stored in `engine-phase-two-team-model-tools-verification.json`.
