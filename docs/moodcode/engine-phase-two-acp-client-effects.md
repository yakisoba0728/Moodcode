# ACP v1 approved native client effects

Moodcode now supports an explicit local stdio ACP v1 client-effect lane. `createEngine({ agentBackends: true, agentBackendClientEffects: true, jobs: true, ... })` enables approved file writes and supervised terminals when the exact registered Run profile exposes `apply_patch` and `run_command`. File writes do not require `jobs`; terminals require the native Run-owned command observer and a supported POSIX command backend. Effects remain off by default. Registration still requires the original host target and exact backend launch/source/configuration pins described in [the backend foundation](engine-phase-two-agent-backends.md).

The connection journals its negotiated capabilities, original launch mode, actual process group, owner and epoch. Unknown capabilities, unsupported content and ACP v2 negotiation fail before client effects. The [official v1 filesystem](https://agentclientprotocol.com/protocol/v1/file-system), [terminal](https://agentclientprotocol.com/protocol/v1/terminals) and [permission](https://agentclientprotocol.com/protocol/v1/tool-calls) contracts guided the wire subset. No external implementation was copied.

A direct `fs/write_text_file` or `terminal/create` request enters the genuine native tool pipeline while the original ACP prompt and native Turn/Attempt remain open. The bridge reserves a native tool call, records its Tool/Part proposal and exact effect input, prepares the existing tool, and waits for a Moodcode approval even when ordinary tool policy allows the tool. The approved dispatch gate holds the actual effect until its original input, profile/catalogue, source/backend revision and native owner are revalidated. Copies of a DTO, historical rows and remote names or descriptions cannot create a runtime handle. Lifecycle input rewrites cannot change client-effect inputs; ordinary model tool rewriting remains supported.

`session/request_permission` is supported for the precise compatibility subset `toolCall.rawInput = { method, params }`, where `method` is one of those two client effects and `params` is the exact later RPC input. Only `allow_once` can spend the actual native approval; permanent remote grants are withheld. The returned option is backed by a native permission source observation and its independent pipe-delivery receipt. Changing content/path/command/arguments/cwd after that approval rejects the request without consuming another effect. Denial returns a rejection or cancellation with no physical effect. Cancellation of a pending permission uses its original session and permission frame; it cannot authorize a new operation.

A write is a single create/update of at most16KiB UTF-8 content through the existing physical patch implementation. The captured current preimage, canonical workspace path and physical parent identity are revalidated before writing. Outside paths, symlinks, physical replacement, mismatched preimages and wider input fail closed. Partial effects and checkpoint gaps retain their original native Tool/Part/checkpoint evidence and uncertainty. A failed wire receipt never rolls back or repeats a physical write.

A terminal is the existing approved `run_command` operation, not a new PTY or fabricated user terminal. Explicit arguments are quoted as literal argv; with no arguments the existing approved shell-command semantics apply. Remote environment additions are unsupported. `terminal/create` returns a handle after native dispatch admission; that acknowledgement is not proof that a process started or completed. `terminal/output` reads a bounded UTF-8 tail from the actual Run-owned command ring without waiting for exit, with honest truncation. `terminal/wait_for_exit`, `kill` and `release` stay bound to the original Attempt and command handle. Concurrent wait and kill share one settlement. Kill/release abort and join the same actual command supervisor/group, including descendants that retain the inherited process group. Released or foreign handles cannot be reused.

The ACP peer transport remains supervised but, in the effect-enabled launch mode, does not hold the workspace command effect lock while waiting for client RPCs. The actual patch or command pipeline owns that lock through physical effect, checkpoint and cleanup. The read-only/default transport retains its previous execution-lock behavior. This separation avoids deadlocking a command requested by a peer whose own transport owns the lock. It does not sandbox a peer's direct OS calls: the fixed executable/source remains trusted, and this lane makes no OS-isolation claim.

Cancellation sends a bounded `session/cancel` notification through the original session response and an observation-only original launch scope, records exact pipe delivery when available, and then cleans the actual owned processes. Its notification or remote acknowledgement is not completion evidence. Process close, effect settlement, response delivery and final remote prompt settlement remain separate. EOF, owner replacement, delayed approval, duplicate RPC identities and a post-ACK command failure cannot create successful receipts. Failure to journal genuine completion or disposal keeps native uncertainty even when the OS process is absent.

The existing DB23 backend revision/head tables are reused; there is no migration or new table. Immutable revisions independently validate actual native Run/Turn/Attempt ownership, exact prepared fingerprint, allowed approval, Tool/Part terminal state, compact completion source, command outcome/PID and full checkpoint digest. Terminal output has its own native source observation. Self-consistently rehashed completion or approval drift is rejected. The recovery frontier accepts an effect still inside a streaming ACP Attempt only when genuine proposed/dispatched source anchors exist, and retains it as unknown; it does not infer completion or restore a handle.

Restart marks interrupted requests/effects uncertain and never replays a prompt or effect. Archive import disables backend definitions and appends paused history, preserving genuine original approvals, Parts, physical results, checkpoints, deliveries and gaps. Inspection and imported histories grant no live original authority. Actual SIGKILL tests cover both a running acknowledged terminal and a physical file write after native Tool/Part/checkpoint but before the client-effect receipt.

[Verification](engine-phase-two-acp-client-effects-verification.json) records focused actual Engine, temp Git, SQLite, stdio peer, OS process and crash tests, typecheck, declaration emit and source hashes. MC2-09c/d are complete for this explicit local v1 engine-owned effect lane. HTTP remote hosts, authentication, reconnect/load, agent-owned context, arbitrary permission DTOs, remote env additions, Windows terminal ownership and escaped process groups remain unsupported. No live account, model, deployment, push or external write was used. E5-13, E5-08, E6-07 and E6-08 remain separate open items; this document does not change the overall goal or work-item ledger.
