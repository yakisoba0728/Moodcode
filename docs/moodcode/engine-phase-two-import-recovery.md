# MC2-03d: explicit imported knowledge recovery and context activation

Archive import records a new native import frontier on the primary connection, alongside the original paused knowledge record. The frontier pins the validated archive, source database logical hash, source storage identity, and bounded original knowledge uncertainty. Imported generation, attempt, candidate, publication, document and receipt rows retain their original identities and bindings. Recovery does not manufacture a producer, confirm unknown cleanup, or replay work.

Database version 15 adds five tables: import frontiers, their current heads, explicit recovery decisions, document activation revisions, and their current heads. Archive validation and recovery logical hashes include these tables. Reimport records a new frontier and invalidates previous resume and activation authority.

Host mutations require `knowledgeImportRecovery: true`. The host captures an original preview, explicitly acknowledges the exact imported uncertainty, and separately resumes the current import. Resume preserves historical pauses and does not activate a document or wake an imported session. Coding, tool and summary uncertainty still require their own recovery. A foreign execution lock remains owned by its original process.

The host then grants fresh current workspace trust and explicitly activates one exact published SQL document. Activation pins the original native publication, completed tool-free generation, confirmed cleanup, sources, document head and receipt, plus the new physical binding and current trust. Existing previews cannot approve a changed document, source, trust, frontier or binding. Deactivation removes context authority and remains available after trust denial or source deletion.

The actual coding context consumer reads the native activation and historical graph in its primary snapshot. It preserves original provenance and adds separate import activation lineage to the context manifest. Whole supplemental messages count against the existing shared context and output reservations. Expired trust, candidate, plan or activation, changed sources, deactivation and revoked document heads remove the contribution; included data is checked again before dispatch.

An accepted imported uncertain owner stays historical after a later native producer changes the workspace barrier. That successor still requires its own exact native recovery. Activation rejects the successor's unresolved uncertainty; its acknowledgment and separate resume preserve both owners' original `cleanup: false` records and grant no provider replay. Historical barrier pins remain evidence of the import and do not become authority over later owners.

Supported relocation is a new database and artifact bundle at the same canonical physical workspace root, with the original root device and inode unchanged. Arbitrary workspace-root or source-pin mapping is not implemented. Physical file and skill publication history stays historical; this lane explicitly activates host-selected SQL documents and does not automatically discover or enable imported skills.
