2026-10-07에 공식 공개 소스만 확인했다. Pi의 canonical 저장소는 [earendil-works/pi](https://github.com/earendil-works/pi)이며 [badlogic/pi-mono](https://github.com/badlogic/pi-mono)는 해당 저장소로 redirect되는 것을 웹 조회로 확인했다. 분석 버전은 `ae92585d3b3e5f1e4b123d14a34314d826d8d9f5`다. OpenCode는 기존 read-only reference checkout의 `4ac0d9c3d169bbe81d9570013effdda3fe24d36e`를 사용했다. 소스·프롬프트·테스트를 Moodcode로 복사하지 않았으며 두 제품을 실행하거나 라이브 모델을 호출하지 않았다.

## 확인한 구현과 의미

Pi README는 agent runtime과 coding-agent를 별도 package로 소개한다. agent-core의 문서와 실제 loop는 application message를 먼저 context transform하고 이후 provider-compatible message로 변환한다. 따라서 영구 기록과 모델에 보이는 이력은 같은 목록일 필요가 없다. 도구 결과가 모두 기록된 다음 다음 turn 준비가 실행되고, 준비 중 수락된 steer는 catch-up polling으로 반영된다. 이 경계는 Moodcode의 safe-boundary projection과 잘 맞는다. 근거: [README package 표](https://github.com/earendil-works/pi/blob/ae92585d3b3e5f1e4b123d14a34314d826d8d9f5/README.md#L72-L84), [agent message 변환 계약](https://github.com/earendil-works/pi/blob/ae92585d3b3e5f1e4b123d14a34314d826d8d9f5/packages/agent/README.md#L43-L60), [다음 turn 준비와 steer](https://github.com/earendil-works/pi/blob/ae92585d3b3e5f1e4b123d14a34314d826d8d9f5/packages/agent/src/agent-loop.ts#L175-L218), [결과 기록과 turn 종료](https://github.com/earendil-works/pi/blob/ae92585d3b3e5f1e4b123d14a34314d826d8d9f5/packages/agent/src/agent-loop.ts#L261-L306), [실제 변환 호출](https://github.com/earendil-works/pi/blob/ae92585d3b3e5f1e4b123d14a34314d826d8d9f5/packages/agent/src/agent-loop.ts#L379-L397).

Pi coding-agent의 compaction은 최근 token 예산을 기준으로 뒤에서 경계를 고르고 `firstKeptEntryId`를 저장한다. tool result를 절단 경계로 삼지 않으며 하나의 사용자 span이 너무 긴 경우 assistant 경계에서 span을 나누고 앞부분을 별도로 요약한다. 현재 canonical projected entries를 기준으로 이전 summary와 retained boundary를 해석하는 구현이 존재한다. 이는 완전한 Run 전체가 한도 내에 있어야 한다는 제한을 완화하는 근거다. 다만 Moodcode의 이번 변경은 요약 호출이 아니라 bounded DB projection이며, 두 기능을 같은 것으로 표시하지 않는다. 근거: [공식 compaction 설계](https://github.com/earendil-works/pi/blob/ae92585d3b3e5f1e4b123d14a34314d826d8d9f5/packages/coding-agent/docs/compaction.md#L24-L49), [split span과 경계 규칙](https://github.com/earendil-works/pi/blob/ae92585d3b3e5f1e4b123d14a34314d826d8d9f5/packages/coding-agent/docs/compaction.md#L100-L136), [cut point 구현](https://github.com/earendil-works/pi/blob/ae92585d3b3e5f1e4b123d14a34314d826d8d9f5/packages/coding-agent/src/core/compaction/compaction.ts#L806-L870), [canonical projection 기반 준비](https://github.com/earendil-works/pi/blob/ae92585d3b3e5f1e4b123d14a34314d826d8d9f5/packages/coding-agent/src/core/compaction/compaction.ts#L872-L933).

OpenCode의 pinned compaction service는 최근 user turn을 거꾸로 추정하면서 token 예산에 맞는 tail을 선택하고 큰 turn을 분할한다. 비용 계산은 retained tail에 대해 지연 수행한다. 별도 prune은 오래된 완료 tool part에 compacted timestamp를 기록해 이후 projection이 내용을 생략하도록 한다. Moodcode는 원본 저장 transcript/replay를 재작성하지 않고 조회 결과만 파생한다. 이것은 관찰한 구현에서 선택한 독립 설계 차이다. 근거: [tail 선택](https://github.com/anomalyco/opencode/blob/4ac0d9c3d169bbe81d9570013effdda3fe24d36e/packages/opencode/src/session/compaction.ts#L223-L269), [prune 구현](https://github.com/anomalyco/opencode/blob/4ac0d9c3d169bbe81d9570013effdda3fe24d36e/packages/opencode/src/session/compaction.ts#L271-L318), [실행 전 compacted projection](https://github.com/anomalyco/opencode/blob/4ac0d9c3d169bbe81d9570013effdda3fe24d36e/packages/opencode/src/session/prompt.ts#L1092-L1098).

## Moodcode의 독립 구현

완료 Run의 기존 whole-group 조회와 GUI/replay 원본은 유지한다. 가장 최근 active Run이 message/byte 한도를 넘으면 처음 user anchor, 마지막 user/steer anchor, 최근 assistant와 그 뒤의 tool-result 묶음을 선택한다. SQL metadata LIMIT는 `maxMessages+1`이며 tool result부터 시작하는 오래된 불완전 prefix는 선택하지 않는다. 가장 최근 필수 assistant/result 묶음이나 anchor가 한도보다 크면 `MODEL_HISTORY_LIMIT`을 유지한다. 사용자 image refs, tool-call arguments, 선택된 assistant의 native replay는 축약하지 않는다.

4KiB보다 큰 선택된 tool content는 SQLite에서 512 Unicode character excerpt로 바꾼 뒤 JavaScript로 전달한다. observation에는 원본 message ID, 원본 UTF-8 bytes, omitted character 수, completeContent=false 및 최대 4개 artifact ID/SHA/선언 bytes와 나머지 참조 수가 표시된다. `toolResult`의 원본 참조 메타데이터는 보존한다. tool auxiliary record는 최신 32개까지 output/error 중복을 제외해 path instruction discovery에 제공한다. 모델 조회에서는 approval preview를 읽지 않는다. 승인 권한 판단은 별도 단일 owner 조회를 사용한다.

`activeWindow`는 선택 전략, anchor IDs, 최근 첫 message ID, 선택·생략 message 수, metadata 반환 행 수, snapshot JSON bytes, tool content projection의 원본/결과 bytes, auxiliary omission을 기록한다. `summarized=false`는 생략된 current-prefix를 요약했다고 주장하지 않는 계약이다. 현재 semantic memory는 이전 완료 Run만 요약하므로 active-prefix 요약은 후속 구현이 필요하다. 검색으로 원문을 다시 찾는 경우에도 과거 결과를 현재 파일 상태나 새 명령으로 활성화하지 않는다.

DB3 migration은 `(run_id,role,ordinal)` expression index와 `attempt_usage`를 추가한다. 긴 active Run은 indexed count로 먼저 분기하여 모든 원문 JSON byte 합계를 훑는 첫 구현의 비용을 피한다. anchor/latest assistant는 역할 index로 찾는다. 총 omitted count 계산은 scoped index count이며 history 규모에 따른 비용이 여전히 남는다. SQL 결과 bytes와 물리 I/O는 다른 값이고 물리 I/O는 측정하지 않았다.

## 사용량 관측과 복구

`putAttemptUsage(attemptId,partialSnapshot)`는 durable dispatched/streaming attempt의 최신 누적 관측을 같은 transaction에서 기록한다. 동일 값은 멱등이며 부분 필드는 merge한다. 감소, safe integer 범위 초과, inclusive input/output보다 큰 cached/reasoning 값은 거부한다. terminal attempt에 새로운 값은 넣지 않는다. snapshot과 v2 usage event가 함께 rollback하므로 실패 직전 관측은 유지되고 실패한 publication만 사라진다. migration은 과거 이벤트에서 attempt를 추정하거나 사용량을 만들어 넣지 않는다.

기존 `providerUsage`는 최근 2,000 matching v1 이벤트의 observed-event-sum이다. 새 `attemptUsage`는 전체 `attempt_usage`의 attempt당 최신 snapshot 한 번을 집계한다. cached input과 reasoning output을 inclusive total에 다시 더하지 않는다. 관측 없음은 null/missing으로 드러내며 실제 청구 정산을 수행하지 않았으므로 billedTokens는 null이다. summary의 별도 attempt/window 집계와도 합산하지 않는다.

## 검증 기록

`native-history.test.ts`는 실제 SQLite에 정확히 1,000/10,000개의 current Run message, 최대 16 tool call의 batch, 중간 steer, 원본/steer image refs, opaque replay, 큰 한국어 결과와 artifact 참조를 넣는다. bounded 조회에 전체 snapshot 호출을 금지하고 pair/anchor/provenance·저장 원문 보존을 확인한다. 초기 whole-byte scan 구현의 10k 단일 조회는 110.7ms였고 역할 index/cardinality-first 구현은 약 13ms였다. 이 수치는 로컬 fixture의 warm 여부가 엄격히 통제되지 않은 단일 개발 측정이므로 제품 latency 보장이 아니다.

별도 fixture는 queue/steer의 attachment clone과 exact retry 충돌, omitted shape, usage partial merge/실패 retry/restart/injected journal rollback, v1→v2→v3 연속 적용과 v3 실패 rollback, archive의 schema3 usage 보존을 확인한다. 모든 validation은 로컬 fixture다. 라이브 모델, provider billing API, GUI, 실제 디스크 I/O와 오래된 active-prefix의 의미 요약 품질은 검증하지 않았다.

### 반복 query와 실제 accounting loop 추가검증

[Current history 측정 JSON](2026-10-07-current-history-benchmark.json)은 exact1k/10k source fixture에서5 warmup 뒤30개 query를 측정했다. snapshot33,505/48,198 bytes, 후보 metadata100행, selected14/21 messages이고 나머지 원문은 보존한다. 해당 개발 실행의 p50은4.56/13.44ms, p95는6.82/27.20ms다. 후보 행 수는 aggregate/session/header 조회 행이나 물리 index 방문수를 포함하지 않는다.

[Actual accounting 검증 JSON](2026-10-07-accounting-review.json)은 실제 createEngine의36 provider turn과560개 서로 다른 line range의 completed read_file 실행, 중간 steer, duplicate/cumulative/trailing usage, terminal reopen 및 실패 주입을 기록한다. 별도8KiB fixture는 steer 없이24turn/92completed reads를 끝내고 초기 goal과 최근4개 call/result를 온전히 유지한다. provider projection이 생략한15개 메시지와 DB window가 생략한95개 원문은 다른 단계의 수치로 관측된다. 어느 경우도 current Run prefix를 semantic summary로 처리하지 않는다.

실제 HTTP429의 관측 전 실패는 같은 Turn 안에서2번째 Attempt로만 재시도한다. 첫 Attempt의 usage는 미관측 상태로 남고2번째 Attempt의9tokens를 한 번 집계하며, 기존 legacy event-sum18tokens는 별도 의미로 유지한다. Native usage journal rollback은 새 snapshot을 남기지 않지만 별도 legacy run.usage 실패는 이미 성공적으로 저장한 observed snapshot을 유지한다. 둘 다 provider를 다시 호출하거나 부분 output을 completed로 확정하지 않는다. 이 accounting/history7개와 readonly receipt3개, 총10개 focused fixture가 통과했고 source noEmit도 통과했다.
