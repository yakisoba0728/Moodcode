# Moodcode 제품·화면 명세

## 첫 버전의 사용자 경험

사용자가 저장소를 열고 작업을 요청하면, Moodcode가 필요한 파일을 확인하고 수정·검증을 진행한다. 사용자는 현재 작업, 실행하려는 도구, 승인이 필요한 행동, 실제 변경된 코드를 한 화면에서 확인한다. 실행을 중지하거나 앱을 다시 열었을 때도 작업 기록과 종료 상태를 확인할 수 있다.

초안의 중심 경험은 **저장소 열기 → 작업 요청 → 진행·승인 확인 → 변경 검토 → 후속 요청**이다. 사용자에게 받은 확정 사항은 Electron 데스크톱 앱과 자체 엔진, 엔진을 먼저 개발하는 순서다. 화면의 중심 경험과 배치는 아직 제안이다. 아래 화면은 엔진을 검증한 뒤 연결할 제품 범위다.

## OpenCode GUI에서 확인한 내용

OpenCode의 GUI는 `packages/app`의 Solid 웹 앱, 이를 탑재하는 Electron `packages/desktop`, 메시지·도구·composer·diff를 제공하는 `packages/session-ui`, 디자인 시스템 `packages/ui`로 구성된다. 실제 desktop renderer가 `AppBaseProviders`와 `AppInterface`를 사용한다. [분석 보고서](../opencode-analysis/07-clients.md), [app 진입점](https://github.com/anomalyco/opencode/blob/907b3bc518fa48e90e8ec24dd327d13eee71c36c/packages/app/src/app.tsx#L393), [desktop renderer](https://github.com/anomalyco/opencode/blob/907b3bc518fa48e90e8ec24dd327d13eee71c36c/packages/desktop/src/renderer/index.tsx#L407).

작업 목록·세션 탭·입력창, 승인·질문 dock, 파일 viewer와 변경 review, PTY 터미널을 분석했다. 파일 viewer를 완성된 IDE 편집기로 해석하지 않았고, GUI 레이아웃 전환과 V2 서버 사용도 별개의 선택임을 확인했다. 소스 분석과 일부 순수 모듈 실행 검증을 수행했으며, 실제 Electron 앱의 전체 실행·시각 검증은 수행하지 않았다.

Moodcode에는 이 분석에서 배운 책임 분리와 사용자 흐름을 적용한다. 단일 Moodcode 계약으로 입력·실행 상태·이벤트·변경 검토를 연결한다.

## 화면 구성

| 위치 | 내용 | 사용자의 결정 |
|---|---|---|
| 상단 | 현재 저장소·branch·실행 상태, 모델 설정 진입 | 어느 저장소에서 어떤 설정으로 작업하는가 |
| 왼쪽 | 프로젝트와 세션 목록, 새 세션 | 작업의 맥락과 기록을 선택 |
| 중앙 | 사용자 요청, 모델 응답, 접고 펼칠 수 있는 도구 단계 | 지금 무엇을 했고 무엇을 기다리는가 |
| 입력 영역 | 요청, 파일·줄 범위 첨부, 계획/실행 모드, 시작·중지 | 다음 작업과 포함할 맥락을 지정 |
| 승인 영역 | 정확한 대상·명령 또는 patch preview, 허용·거절 | 해당 도구 행동을 실행할지 결정 |
| 오른쪽 | 예정/적용된 변경, 파일 viewer, 실행별 diff와 현재 Git diff | 변경이 의도에 맞는지 확인 |
| 하단 확장 영역 | 명령 출력, 이후 단계의 대화형 터미널 | 검증 결과나 직접 실행 상황을 확인 |

넓은 화면에서는 왼쪽 목록·중앙 작업·오른쪽 변경을 함께 보여준다. 좁은 창에서는 변경 영역을 탭으로 전환하고 입력·승인·중지 동작을 유지한다. 작업 흐름 중심 배치는 중앙 timeline을 넓게, 변경 검토 중심 배치는 diff를 넓게 배치한다.

## 대표 사용 흐름

1. 앱 실행 후 폴더 선택기로 로컬 Git 저장소를 연다. 현재 branch와 기존 수정 파일을 표시한다.
2. 설정에서 모델 연결을 확인하고 새 세션을 만든다. 첫 공급자·인증 방식은 별도로 정한다.
3. 요청과 파일 맥락을 입력한다. 실행 설정은 제출 시점에 고정하고, 접수 확인 후 입력창을 정리한다. 접수 실패 시 새 편집을 덮지 않고 초안을 유지한다.
4. 읽기·검색·응답·도구 결과를 timeline에 표시한다. 모델이 반환한 실제 이벤트를 사용하고 가상의 완료율을 표시하지 않는다.
5. 파일 쓰기·명령 실행의 승인이 필요하면 정확한 요청을 보여준다. patch 승인은 적용 예정 코드와 현재 파일의 버전을 묶는다.
6. 승인 후 실행 결과와 변경을 표시한다. 거절 결과는 엔진으로 돌아가고, 이후 대응도 timeline에 남는다.
7. 사용자가 중지하면 취소 요청과 취소 완료를 구별한다. 완료·실패·사용자 취소·프로세스 중단을 서로 다른 상태로 표시한다.
8. 실행 후 이번 작업의 변경과 현재 Git 변경을 따로 볼 수 있다. 기존 사용자 수정은 유지한다.
9. 앱을 다시 열면 기록을 복원한다. 중단된 실행은 `interrupted`로 표시하고 후속 실행을 명시적으로 시작한다.

## 첫 사용 가능한 버전

| 기능 | 범위 |
|---|---|
| 프로젝트 | 로컬 Git 저장소 열기·최근 목록·branch·변경 상태 |
| 세션 | 생성·목록·요청·스트리밍 응답·기록 복원 |
| 자체 엔진 | 단일 세션 agent loop, tool result를 다음 model turn에 반영 |
| 모델 | 공급자 하나의 텍스트·tool calling·usage·오류·취소 |
| 도구 | 파일 목록·읽기·검색, patch 적용, 명령 실행 |
| 승인 | 도구 호출별 대상과 동작을 보여주는 허용·거절 |
| 검토 | patch preview, 적용된 실행별 변경, 현재 Git diff, 읽기 전용 파일 표시 |
| 운영 상태 | 도구 출력 제한·timeout·명시적 중지·재시작 후 기록 복원 |

대화형 PTY, 추가 공급자·OAuth, context compaction, worktree 병렬 작업, subagent, MCP·플러그인, 편집기·LSP, 원격 실행, TUI는 후속 단계로 둔다. 이 순서는 제품 우선순위가 정해지면 바뀔 수 있지만, 실행·승인·변경 보존 계약은 먼저 검증한다.

## 첫 버전의 완료 조건

- 별도 개발 서버·소스 checkout 없이 패키징된 앱에서 저장소를 열 수 있다.
- 실제 공급자와 도구를 이용해 작은 코드 변경 및 검증 명령을 완료한다.
- 승인 전 쓰기/명령 실행이 발생하지 않으며, 파일이 바뀌면 오래된 patch 승인을 재사용하지 않는다.
- 같은 저장소의 변경 실행은 한 번에 하나다. 추가 제출은 초안을 유지하며 실행 중임을 설명한다.
- 중지 후 provider·도구·자식 프로세스가 정해진 취소 계약에 따라 정리되고 상태가 확정된다.
- 앱 또는 엔진을 재시작해도 기록을 복원하고, 이전 도구 행동을 자동 재실행하지 않는다.
- 실행별 변경에 기존 사용자 수정이 잘못 포함되지 않으며, 복원 충돌을 표시한다.
- 긴 출력과 연속 token 이벤트가 입력·중지·승인 동작을 막지 않는다.
