# Native workflow and recipe engine

Moodcode implements bounded workflow definitions, recipe parameter binding and explicit readonly stages through its existing owned child engines. This increment covers MC2-07a/b and the readonly foundation of MC2-07c/d. Editor/validator execution, approved merge, role/model escalation and automatic parent result delivery remain open work items.

`workflows: true` enables the host operations. `registerWorkflow` stores an immutable definition revision; `previewWorkflowStart` captures the actual live parent, exact profile/model/catalogue, remaining budget and pre-created managed worktrees. `startWorkflow({ approved: true, preview, ... })` accepts only the original preview. Each explicit `startWorkflowStage({ approved: true, ... })` records a native dispatch intent, reserves the existing parent child budget, admits an actual isolated child and records its original admission. `observeWorkflowStage` observes that child and commits its complete structured result. `getWorkflow` and `inspectWorkflow` remain readonly history APIs when orchestration is disabled.

Definitions contain at most eight stages and a dependency longest path of four. Runtime child nesting retains the existing limit of three. Parameters and results use a bounded JSON schema subset, object `additionalProperties: false`, explicit required fields and bounded strings/arrays/enums. Cycles, unknown dependencies, duplicate stages, unsupported fields, accessors, proxies and incomplete result bodies fail before effect admission. Recipes pin the exact definition hash and bind inputs as advisory data.

Planner and advisory-reviewer stages inherit the exact actual parent profile, provider, model and reasoning setting. Their tools are the explicit readonly subset of the parent's unchanged actual catalogue. A role label or a prior stage result grants no additional tool, edit, profile or model authority. Parent turn/tool/output reservations use the existing child admission boundary; duplicate dispatch cannot reserve again. Stage results require complete, untruncated child JSON within four KiB and the declared stage schema.

DB19 adds `workflow_revisions` and `workflow_heads`, both STRICT WITHOUT ROWID tables. Definition, instance, stage and transition revisions retain request hashes, predecessor identity and exact owner/proof hashes. Head updates and transition receipts commit in one transaction. All/any joins use persisted dependency selections; accepting another child completion cannot replace already selected advisory data. Sibling execution is not implicitly cancelled.

Original admission/completion handles come from the private actual child engines, their native task journal, admitted Run configuration, root/child storage proof and measured coordinator usage. Caller-described child IDs or copied handles cannot substitute for that producer. Existing work can settle after parent cancellation without granting new dispatch. Cancelling a host observation stops that observation promptly; its original child remains available for a later explicit observation.

Interrupted dispatching/running stages become uncertain on restart and never replay automatically. Archive validation checks the local native revision/receipt graph and child admission relationships without opening foreign child paths. Import appends paused-import history and restores no runtime owner or execution authority. Historical readonly inspection works with orchestration disabled.

The actual primary SQLite catalogue has 130 non-internal rows. The recovery metadata cap is 160; inclusive and excessive boundaries and unknown tables are tested. Historical DB18 and earlier migrations and logical hashes retain their original schema.
