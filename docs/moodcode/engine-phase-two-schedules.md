# Durable scheduled input admission

Moodcode's scheduling engine is an explicit root-host feature. `schedules: true` enables root worker, target and dispatch capabilities; isolated child engines keep it disabled. A schedule never bypasses the existing session queue, execution approvals, workspace quarantine or Run budgets. Clock polling and external webhook delivery remain host integrations.

The actual root captures the workspace's physical database/artifact/root identity, exact normalized Run configuration including all budgets, registered profile revision, provider, full effective tool catalogue and capability hashes. Schedule registration requires its original root target. Serialized pins are inspectable data and cannot reconstruct runtime authority. Dispatch writes its native intent before making one synchronous `InputScheduler.accept` call. An original actual acceptance receipt is committed separately; an uncertain gap cannot authorize acceptance replay.

Absolute and daily schedules have explicit starts/end boundaries, IANA timezone and runtime timezone-data version. Daily folds choose earlier/later/both/skip; gaps skip. Catch-up emits at most32 due occurrences per batch and advances a persisted cursor; latest and skip have explicit missed-run semantics. A clock moving backward retains the high-water mark. Due batches are calculated by the root's actual clock, and cursor advancement plus materialization commit atomically against the current schedule revision. After re-registration, a due slot an earlier revision already claimed is omitted rather than materialized again. Candidate JSON grants no time, worker or dispatch authority.

Webhook bodies use a strict bounded object schema and at most8KiB of untrusted advisory data. A secret reference stores no secret body. External integrations must authenticate a webhook before calling the trusted root-host capture API. A formatted input separates the host's fixed prompt from the quoted event data. Repeated event identities preserve the first native occurrence rather than creating another input.

DB20 adds two STRICT WITHOUT ROWID tables, `schedule_revisions` and `schedule_heads`. Immutable revisions and request-preimage receipts preserve schedules, worker leases and occurrences; head changes use native revision CAS. Import disables schedules and appends paused-import occurrence history. Interrupted claim/dispatch states become uncertain and never automatically replay. Ordinary appends fail with `SCHEDULE_LIMIT` when they would leave the journal too little room for that recovery and for import. Lease expiry and disable are dispatch fences; neither proves termination nor cancels a previously accepted input or running Run.

Immediately before queue promotion, the scheduler checks an occurrence's historical exact target pins. A changed profile, tool catalogue, physical workspace or capability snapshot stops promotion before a Run is created. The check also identifies an accepted input in the dispatch/receipt gap, so ordinary session resume cannot bypass a missing receipt. Historical inspection remains available with scheduling disabled.

The same historical pins are checked synchronously at actual provider entry, after all awaited context and lifecycle checks. Profile changes during async context construction cannot admit a stale scheduled Run. Native graph replay checks operation/state meaning and actual local Input/Run ownership, so a consistently rehashed false terminal state is rejected. Ordinary queue inputs use bounded metadata lookup without materializing all scheduled bodies.
