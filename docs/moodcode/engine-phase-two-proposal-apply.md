# MC2-05c/d — original approved host proposal effects

The idle host applies a saved native ProposalSet through a separate `proposalApply: true` opt-in. `previewProposalApply` prepares an original exact preview; `applyProposal` consumes that same preview with explicit approval. It binds the actual native proposal/revision/head, captured source manifest, current physical workspace and storage identity, physical file/parent pins, preview hash and deadline. A copied preview or a changed file/head/root requires a fresh preview. Unused expired previews are released when the next preview is prepared. Denial, invalid input, stale source and pre-dispatch cancellation do not grant target write authority.

The application lane supports one complete proposal with at most 32 files, 1 MiB per file and 4 MiB combined before and desired after images. The larger stored 128-file/8 MiB proposal can still be inspected and used as pending DATA, but application rejects it before artifacts are loaded or an effect owner/lock is created. It never splits one approval into multiple effect batches. Windows hosts are refused at preview with `PROPOSAL_APPLY_UNSUPPORTED`, before any owner exists, because execution guards accept only POSIX lock paths.

Database version 17 records host-native apply owners, exact observed checkpoints, dedicated actual postimage BLOBs, immutable receipts, separate recovery decisions and physical execution guard intents. These rows own their workspace, proposal, revision and apply identity. They do not fabricate a coding Session, Run, tool call or Run checkpoint. The existing `apply_patch` tool uses the same physical producer while retaining its actual outer tool approval and Run-owned checkpoint.

The service admits an idle workspace lease. Before effects it requires at least ten seconds of preview validity and an available shared effects lock; a refusal there cancels the owner, since nothing was reserved. It then commits the execution reservation intent and the owner claim in one transaction before acquiring the lock, and checks every original source and native head again. Native dispatch is durable before the first mkdir, write, truncate or unlink. The physical producer performs the approved changes once. On failure or cancellation it joins the original descriptor operations and records complete actual observations where possible. Unknown postimages remain distinct from confirmed absent files; partial results preserve surviving bytes and created-parent observations without automatic rollback.

The exact producer-owned result supplies native checkpoint authority. Checkpoint and postimage artifacts are committed while the execution guard is held. The service releases the original lock only with observed descriptor cleanup, then commits the immutable receipt and head CAS. A receipt marks applied, known partial or uncertain. Applying changes advances the mutable head version without inventing another content revision. Original version-16 revision and artifact hashes are retained. New content after a terminal apply head requires a fresh ProposalSet in this first lane.

The same original approved request returns its historical native owner/checkpoint/receipt before another source read, lease or producer. This does not restore an old head or repeat an effect. A revision is applied at most once: any owner consumes it, including a cancelled one that changed no file, and a new request for it fails with `PROPOSAL_APPLY_REVISION_USED`. Append a new revision to apply again. Read-only `getProposalApply` and `getProposalApplyRequest` expose history even when authoring and application are disabled. After restart, callers inspect that durable history; ephemeral approval and result capabilities cannot be reconstructed from the stored JSON.

Interrupted owners are never reapplied. Guard-free prepared owners can become cancelled; a prepared owner with persisted guard intent and every dispatched owner become uncertain. The guard-only crash gap retains cleanup uncertainty even when no target write was observed. Checkpoint persistence failure retains the marker, and release-before-final-settlement failure retains the uncertain owner and any actual checkpoint. Workspace admission remains blocked until separate explicit acknowledgment and resume decisions are recorded against the exact original recovery frontier. Original uncertainty and false cleanup are preserved; decisions never convert them into successful application or automatically wake queued work. The physical reconciliation accepts only an exact known stopped marker and leaves foreign markers untouched. Acknowledgment while another supervisor holds the effects lock fails with the retriable `COMMAND_EFFECTS_BUSY`.

Archive validation checks native proposal, apply owner, artifact, checkpoint, receipt, head and guard relationships. Import preserves the original evidence and pauses proposal heads. An imported physical guard is historical data; it does not rebind an old path, device/inode or storage identity to the new host. An archive with an active physical effects marker is rejected by the existing `ARCHIVE_EFFECT_ACTIVE` boundary; this increment does not export that unresolved effect state. Unknown imported physical claims cannot be automatically cleared or replayed. Sequential Node filesystem observations do not establish an atomic OS snapshot/hash CAS against external writers.
