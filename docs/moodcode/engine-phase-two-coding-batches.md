# MC2-20 — coding attempt groups and headless batch consumption

This increment implements a complete supported local host path: original batch preview and explicit admission → genuine independent editor/validator/reviewer child Engines → native verification and advisory review receipts → original selection preview → separately approved native merge → atomic result inbox admission → a real consuming Run. It reuses the existing workflow/effect/merge/input implementation, DB 23 SessionDocuments and independent native events. No migration, synthetic control Run, new scheduler or copied effect producer is introduced.

## Supported configuration and host flow

Enable `codingBatches: true`, `workflows: true` and `verificationTools: true` on the root Engine with its core tools. Register a real profile with the needed workflow/edit/verification handlers and registered verification checks. A batch requires an actual live parent Run admitted through the normal Engine `run.submit` path. The host can orchestrate it without a GUI; this increment does not create a fabricated standalone control Run. Custom ToolDefinitions as effect producers, alternate profile/model escalation and imported/reopened live actors are unsupported. Child Engines always have `codingBatches: false`.

Pre-create managed worktrees before the parent owns its workspace execution lease. A group has one to four cases, each represented by its own native workflow instance with exactly three stages: `edit` (editor), `validate` (validator), and `review` (advisory reviewer). Editor and validator intentionally share their case worktree sequentially. Each reviewer has a separate worktree, and no worktree is shared between different cases. Every actual stage uses a distinct child Engine, database, artifact directory and native child admission. A problem-level coding attempt is this case/workflow instance; its native provider Attempts remain separate nested request identities.

1. `previewCodingAttemptGroup` pins the group/case specs, actual source file identity/hash, parent profile/model/config/catalogue, verification plan, managed physical worktrees, fixed allocations and limits. `startCodingAttemptGroup` requires that Original preview and explicit `approved: true`.
2. Before the first child, all member turn/tool/output allocations reserve actual parent capacity together. Slots are Original, single-use and never refunded. Native group-birth failure does not permit a second reservation using the old preview. `runCodingAttemptGroup` admits at most the declared concurrency and dispatches only the fixed stages and reservations.
3. Editors execute their normal approved native patches. Validators execute actual registered `verify_changes` checks through native tool/approval/process/artifact/checkpoint paths. Reviewers receive quoted predecessor DATA and can use only their readonly selected handlers. Native child Run/Turn/Attempt/Tool/Part/checkpoint/cleanup and verification receipts determine success. A fulfilled future, predictions ID, cancelled task or high review score cannot produce a verified case.
4. `inspectBatchEvidence` reads the signed native group and case history. `previewCodingAttemptSelection` rechecks the actual candidate files, check registrations/artifacts, current parent HEAD and source. `selectCodingAttempt` requires the Original preview and explicit approval and stores a native selection revision. Reselection before merge is allowed and invalidates any pending old merge approval.
5. Selection binds the chosen case to the existing actual parent `merge_workflow_stage` tool. Its Original Runner ToolContext, native prepared fingerprint and separate exact approval are required. Preparation and execute pin the selection revision/hash in addition to the normal file/check/HEAD evidence. The actual native merge receipt and the group selection receipt share the outer primary transaction. The host does not construct a ToolContext or grant an implicit merge approval.
6. After a confirmed native merge, `captureCodingBatchDeliveryTarget`, `readCodingBatchDeliveryTarget` and approved `deliverCodingBatchResult` reuse the existing atomic workflow result admission. Actual `acceptInput`, signed native result receipt and independent input-linked event commit together; wake occurs after COMMIT. One bounded `[Moodcode workflow result DATA v1]` input is consumed by a real subsequent Run. The source terminal Run receives no new execution events.

Additional APIs are `skipCodingBatchCase`, `cancelCodingAttemptGroup`, `resumeVerifiedBatch`, `captureBatchEvidenceExport`, `readBatchEvidenceExport` and `releaseCodingAttemptHandle`. Returned results are copies; export and admission handles are Original runtime capabilities. Original handles are never recreated from a DTO or history.

## Fixed bounds and accounting

Group/case concurrency is at most four; group duration is at most five minutes. Selected source bytes are at most 1 MiB across at most 32 declared files per case. Evidence is capped by both the selected limit and the native document/JSON structural bound; export is at most 2 MiB, and existing workflow result text is at most 32 KiB. Native group/case documents are capped at 256 globally with at most 16 groups per workspace. Runtime previews are capped at 16; selection/export handles at 32 each, and retained operation requests at 128. Existing workflow eight-stage/depth-four and catalogue limits remain unchanged.

Actual turn/tool/output reservations are paid up front for every member, including skipped or failed members. Request accounting charges one time at the actual original provider entry, rather than at repeated freshness callbacks. The token reservation uses the actual normalized maximum context bytes, maximum provider attempts and stage output allocations as a conservative text request/output envelope. Known numeric nonnegative token pairs are accumulated from genuine native AttemptUsage records; absent, partial or null fields remain unknown and are never treated as zero. Unknown requests remain counted.

`costPerRequestMicros` is an explicit fixed host accounting policy, reserved for the maximum request count and charged per actual request. `maxCostMicros` bounds that policy ledger. It is not a verified external invoice or a promise about hidden provider reasoning/pricing. Live provider billing and provider-specific tokenizer/invoice enforcement are outside this local fixture lane; this limitation is preserved rather than calling unmeasured cost zero. Child deadlines and actual parent turn/tool/output budgets remain enforced by the existing Runner.

## Partial results, resume and ownership

Cases distinguish pending, running, verified, failed, skipped, cancelled and uncertain. A pending skip can be explicitly resumed within the original current lifetime using its existing reserved slot. Verified or failed/effected attempts are never replayed. Resume rechecks source/runtime/config/catalogue, managed worktrees, actual verifier/artifact evidence and any captured export fingerprint before admitting pending work. Already merged selection/result receipts do not reapply files or reaccept inputs.

Running cancellation aborts the genuine child task owners and joins actual cleanup. A provider iterator return that does not confirm completion produces uncertain child and group history. Cleanup debt, original reservations and already produced effects remain intact. Parent owner loss, expired deadlines, changed source/HEAD/profile/catalogue/artifacts and unknown cleanup cannot restore dispatch authority. Cancelling the group retains the parent Run's own existing lifetime rules.

Actual candidate editor/validator identities remain tied to their observed receipts even after merge or paused import. The native reader follows the independent immutable effect-event ancestor chain and checks the exact stage/source/child completion/files/artifacts identity; a state string alone never exempts an original editor hash.

## Recovery, archive and irreversible boundaries

Native history uses reserved `coding.group.*` and `coding.case.*` SessionDocuments and independent `coding.group.recorded` / `coding.case.verified` events. Full archive/recovery validation checks signed bodies, current document CAS, actual workflow and child history, verified receipts and original selection lineage. Reopen marks interrupted active groups/selection uncertain and never reconstructs reservations, actors or children. Archive import pauses groups/effects and preserves native IDs, hashes and verified evidence as history only.

Actual physical merge followed by native receipt failure preserves changed files and uncertain debt; it never reapplies the patch. Before atomic result COMMIT there is no input/result receipt. After COMMIT exactly one pending accepted input and receipt remain. Default-off reopening permits readonly inspection. An accepted local pending result can be consumed after explicit session resume with the unchanged workflow/config/catalogue/source pins; batch execution/selection authority is still unavailable. Imported pending result/history cannot auto-dispatch, merge or recapture an Original source.

The local host orchestration depends on the actual engine-owned workspace/execution leases and physical file/check/artifact checks. This is not a new OS sandbox or an atomic kernel snapshot against hostile external filesystem writers. The independent sandbox lane and environment debts E5-13, E5-08, E6-07 and E6-08 remain unchanged. No external code, account credential, live provider, GUI, push or deployment is used.
