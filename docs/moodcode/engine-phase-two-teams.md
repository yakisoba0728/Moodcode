# MC2-06a/b — native teams, mailboxes and task ownership

`teams: true` explicitly enables host-managed team effects. The default is false, and child engines retain `teams: false`. Native team metadata is not a copied session blob: database version 18 adds seven STRICT WITHOUT ROWID tables for immutable state revisions, CAS heads, messages, cursors, operation receipts, delivery records and delivery receipts. The actual schema has 128 catalog rows, within the existing 128-row recovery limit.

`createTeam` writes metadata without dispatching a provider or changing workspace files. `previewTeamMember` captures an ORIGINAL root or child owner from the actual engine execution, its root/session/Run lineage, physical workspace/storage pins and cleanup observation. `joinTeamMember` consumes that original preview with explicit approval. Callers cannot supply an owner hash or reconstruct authority from saved JSON. Root owners must belong to the current engine coordinator; child owners must belong to its actual execution and admitted child storage record. Permissions, expiry, selected alias, member revision and generation are checked again inside native mutations.

`retireTeamMember` requires the captured original owner and observed confirmed cleanup. A confirmed closed child can retire its old member generation before a fresh actual child is approved for a new generation. Unknown cleanup, a paused or cancelling parent, a terminal recipient and an unresolved delivery do not grant live ownership. Several member aliases for the same child cannot bypass execution uncertainty, and a worker alias cannot borrow a coordinator alias's board authority.

`sendAgentMessage` persists a complete message and immutable receipt before returning success. Sender and recipient generations are exact, and the recipient is checked against its actual live execution inside the transaction. Historical duplicate requests return their original receipt before asking for fresh live ownership; a changed request under the same identity conflicts without effects. `readAgentMailbox` returns an ORIGINAL bounded page with an exact serialized byte count. `claimAgentMailbox` commits its receipt and cursor CAS. A page holds either live messages only or expired messages only; an expired page can be claimed to acknowledge it but never delivered. Later sends do not alter an already captured page. Claiming a page does not run a child.

The supported bounds are eight active, unexpired teams per workspace, 32 members and 128 tasks per team, 4 KiB complete UTF-8 message text, 256 pending messages / 1 MiB per mailbox, and at most 64 messages per page. The message-content allowance is 48 KiB within a 64 KiB complete page DTO. At most 128 original pages and 32 / 1 MiB active delivery captures are retained; TTL is at most one hour. Limits reject whole inputs rather than silently truncating them. Read-only list methods return bounded prefixes, not an unbounded task scan.

`putTeamTask`, `claimTeamTask` and `completeTeamTask` use native revision/head CAS and exact request receipts. Dependencies, coordinator management permission, selected worker claim permission and immutable task-owner member revision are checked. Task completion is board metadata; it is not a coding validation result or permission to merge files. Read-only `getTeam`, `getTeamMember`, `listTeamMembers`, `getTeamTask`, `listTeamTasks` and `getTeamDelivery` remain available independently of the effects opt-in.

The current live-child continuation groundwork is explicit host `resumeChildTurn`: an approved ORIGINAL mailbox page becomes native prepared and dispatched records, then is accepted into the actual original child's current Run as a `steer` input. Its original input record and normalized Run configuration provide acceptance authority. The root delivery receipt and mailbox cursor settle atomically after actual child acceptance. The existing InputScheduler promotes that input only at its safe boundary; it cannot rewrite a pending approval, a frozen tool effect or a same-Turn retry. This API does not create a new Run, wake a terminal child, replenish budget or reset the parent deadline.

The cross-database interval between child acceptance and root receipt is deliberately uncertain after interruption. Reopen cancels undispatched prepared deliveries and marks dispatched ones uncertain; it never reissues a message or wakes a queued Run. The pending cursor, actual child input and historical receipts are retained. An uncertain execution tuple quarantines every alias and replacement attempt for that same original child, while unrelated children remain independent. Explicit uncertainty acknowledgment/resume is a remaining task.

Primary-only native validation checks the typed local graph and historical root child-storage pins. It cannot prove the existence of an input in an unavailable child database. The live bridge establishes that proof from the original actual child; archive validation additionally uses `validateTeamChildInputRelations` with an already audited typed child reader. This pure helper opens no path: it compares actual indexed child input/Run rows, normalized request SHA, admission sequence, deterministic delivery request ID and full mailbox prompt. A later input promotion or cancellation preserves the original acceptance observation. Wrong actor, wrong input identity, hash-consistent altered request and modified actual child text are rejected.

Export and import preserve immutable team histories. Import adds a paused-import team head and grants no live membership, delivery replay or owner rebinding. Delivered team evidence requires an exact typed child audit. Missing coverage is `ARCHIVE_TEAM_CHILD_UNCHECKED` unsupported; an incorrect audited relation is `ARCHIVE_TEAM_INVALID`. Re-export of imported historical deliveries can be unsupported when their old child cannot obtain that exact typed audit. No historical path is reopened to manufacture evidence.

Independent checks include real public Engine/Git fixtures, nine native tests, public host and bridge proofs, four actual child-input/archive relation tests, and four genuine SIGKILL boundaries: prepared commit, dispatched commit, child acceptance before root receipt, and completed receipt commit. The child is stopped at an observable committed boundary and killed by the parent; these cases do not substitute a simulated exception for process death. Fixture parent/child budgets and original provider iterators remain intact.
