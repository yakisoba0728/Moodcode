# Resident child teams and model task workflow

This increment uses the existing actual engine-owned child, managed Git worktree and separate child SQL store for several sequential Runs. `residentTeams: true` also requires explicit `teams: true` and `teamModelTools: true`; all three remain off by default. `previewResidentChildTask` captures an ORIGINAL current parent/configuration/profile/catalogue/worktree preview. `startResidentChildTask(preview, true)` consumes that exact host approval. Copies, altered source, role/profile/tool escalation and denied approval cannot dispatch a child. `readResidentChildTaskPreview`, `releaseResidentChildTaskPreview`, `inspectResidentChildTask` and `stopResidentChildTask` provide bounded host inspection and lifecycle control.

The first child Run may finish while its actual task and Engine remain alive. An explicitly approved ORIGINAL mailbox page then follows the native prepared/dispatched delivery path. Resident acceptance persists a queue Input and a new Run in that same child store; the Root stores its actual receipt and mailbox ACK together. Only after that commit does the private bridge release the next provider. If the current source changes between committed ACK and release, the durable receipt remains and the bridge immediately cleans up and quarantines the unstarted Run. Its original parent, child storage/worktree, actor/member generation and runtime epoch stay fixed. Actual latest Run/Tool/Turn/Attempt/Part identities are checked by the private coordinator; no serialized context, historical owner or imported actor becomes a producer.

A parent reservation covers the entire resident lifetime. Each later Run receives the remaining measured turns, tool calls and output bytes, the same inherited model/profile/catalogue, and the remaining original deadline. The parent does not receive fresh credits for mailbox arrivals or role labels. Normal completion leaves the child idle; budget exhaustion, bounded idle TTL, lifetime deadline, explicit stop, parent cancellation and host close wait for genuine provider/process cleanup before settling the task. A real Node command cancellation test observes its PID disappearing before settlement. Unknown iterator cleanup or accepted input without a committed ACK remains uncertain and blocks continuation, replacement and automatic takeover. Nested delegation/merge tools are explicitly unsupported for a resident request before effects because that allocation transfer is not part of this lane.

The actor-bound model catalogue adds `read_team_board`, `submit_team_task` and `review_team_task` to the existing message/claim/complete tools. Board reads return complete bounded one-task pages with description/dependencies, an explicit continuation task ID, and latest submission/review DATA. Each captured read remains frozen. Submit is available only to the exact current claimant; review requires an independent coordinator with task-management permission. Both use exact native approval, including the real outer approval fingerprint and the inner request fingerprint. Advisory text and mailbox messages are quoted DATA. File changes, commands, verification and merges retain their ordinary independent approvals; a review is not a validation or execution grant.

The actual demonstrated workflow is model claim → native `read_file` work → approved submit → independent approved model review → native task completion. Completing a submitted task without its approved review is rejected. Task completion, board CAS and the typed `team.workflow.committed` source anchor share one primary transaction. An injected review receipt failure rolls back all three. The same request returns its durable result without another board/task transition, while conflicting input is rejected. Two actual resident claimants sharing the same expected task revision produce exactly one winner.

No migration is added. DB23 still has 139 named catalogue rows within the 160-row recovery limit. Signed bounded resident and board records use existing session documents and typed native events. Limits are eight resident admissions per current Root, 32 retained host previews, 32 resident histories globally, 32 Runs per resident, 128 board histories and 16 submissions per board. Record limits are 64 KiB/32 KiB; their maximum aggregate head size is below the fixed 8 MiB validator bound, so admission caps preserve capacity for terminal, recovery and import updates. Existing team/member/mailbox/claim limits remain unchanged. Model input is 8 KiB, advisory text 4 KiB, actor capture 32 KiB, board page 24 KiB and tool output 32 KiB; a too-small actual Run output allowance rejects the whole result.

Open/recovery checks native document/event and immutable task/member relationships. Archive checks also compare submissions/reviews against the actual Root or audited child Tool/Turn/Attempt/Part, exact allowed approval and original input. A real altered Root approval fails archive validation. Multi-Run child archives require the original resident mirror and exact actual child history. Import preserves records and ACKs while adding paused-import history; it restores no live actor, provider wake or execution capability. Reopening an interrupted resident retains uncertain ownership instead of replaying the accepted input. Genuine SIGSTOP/SIGKILL fixtures cover dispatch, child Input admission before ACK, ACK before provider release, completed child Run and committed submission before Tool-result delivery.

The feature is frozen for Root integration after focused source, adjacent regressions, strict whole-project declaration build and formatting checks. The aggregate goal and progress are owned by Root. Fresh activation of imported/uncertain ownership, detached lifetime beyond a terminal parent, foreground/background ownership transfer and nested resident allocation transfer are outside this supported lane. No live account/model or additional OS support is claimed. Evidence is recorded in `engine-phase-two-resident-teams-verification.json`.
