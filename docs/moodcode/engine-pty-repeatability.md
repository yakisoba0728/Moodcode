# Native PTY repeatability

`node scripts/verify-pty-repeatability.mjs` repeats five deterministic, local Engine PTY scenarios eight times. It uses the compiled Engine by default. Build first with the repository's normal build command. For a focused source investigation without changing `dist`, use:

```sh
node scripts/verify-pty-repeatability.mjs --runtime source --iterations 3 --timeout-ms 10000 --max-duration-ms 120000
```

The scenarios are normal exit, stdin plus resize, cancellation with a native descendant, actual supervisor SIGKILL, and actual IPC disconnection. The verifier delegates to the original POSIX backend and captures its `closed` outcome. The supervisor, native PTY, shell, process snapshots and kernel probes are genuine. Observation listeners retain actual supervisor result frames, process exit, IPC disconnect, stdout EOF and `close` delivery; they do not replace native results or inject favorable cleanup observations. No live provider is registered, no run is submitted, and no credential reader is invoked. The aggregate report explicitly records `noLive: true`, `liveProviderRequests: 0`, and `credentialsRead: false`.

Normal exit and stdin/resize require `completed`, exit code zero, observed native exit, observed supervisor `close`, and `cleanupConfirmed: true`. Cancellation requires its actual known cleanup and cancelled outcome. Supervisor faults require the current conservative `uncertain`/`supervisor_lost` result with `cleanupConfirmed: false`; an unexpected genuine variant fails and retains its actual data. Physical PID and PGID disappearance is checked separately and does not grant cleanup authority. Unknown probes, including EPERM, never count as absence. Missing ancestry and leader loss retain their uncertainty.

Every case retains `engine.sqlite`, the terminal SQLite sidecar, artifacts, `case.json`, and bounded worker logs in a fresh directory. Passing expected faults retain their uncertain journal records. The JSON report records backend outcome, final terminal diagnostics, native and supervisor PIDs, observed PGIDs, supervisor event ordering, kernel presence and error codes, and SQLite/restart comparisons. Restarted history must preserve diagnostics and reject attempts to regain a live Original source or write terminal input. Reports use mode 0600 and fixture directories use mode 0700. The verifier never deletes evidence or acknowledges recovery.

The report's `sourceIdentity` reuses the existing Engine evaluation inventory of production sources and the effective Engine/contracts runtime. `runtimePins` additionally hashes the CLI, runtime executable, loader when used, lockfile, shell/process inspection binaries, node-pty package and loaded native module/helper. Before/after inventories must agree. This is a bounded scoped inventory, not a claim that every dependency or repository file is attested. A source run qualifies that selected source runtime; a compiled run qualifies the selected compiled runtime. The script never builds automatically.

`--iterations`, `--scenarios`, `--timeout-ms` and `--max-duration-ms` bound work; `--output` selects a new evidence directory and `--report` selects the aggregate report. Cases execute sequentially in a fixed scenario order. Boundary timeout or failed assertions stop the batch with its evidence retained. The watchdog sends SIGTERM through its original live worker handle so the worker can join Engine cancellation. It allows one second of grace before SIGKILL of that same worker. A failed Engine close can use the worker's retained original `PtyProcess.cancel()` handle. The parent only records presence of historical PID numbers after a timeout; those observations never authorize signals, recover physical ownership, or confirm cleanup. Original outcomes and unresolved evidence remain failures. The batch deadline permits that bounded one-second cancellation grace plus final report I/O.

Exit zero means all requested scenarios passed with stable pins. Exit one means failure. Exit two means invalid CLI or unavailable native support. `status: unsupported` and `nativeQualified: false` provide no native credit. Only the current supported Darwin/Linux/FreeBSD POSIX backend qualifies; Windows Job Object/native PTY behavior is not qualified.

Historical hosted `R-PTY-01` remains unexplained. Repeated current passes do not identify its original close reason, resolve its cause, or reclassify it. The separately reproduced Node 26 IPC-disconnect/exit/stdout-EOF missing-`close` correction is already covered by current diagnostics. A future lifecycle failure will now retain the original close outcome and physical evidence needed for diagnosis without weakening cleanup semantics.
